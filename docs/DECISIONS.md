## D002 BEIR data from the original zips, verified by SHA-256
- Date: 2026-11-10
- Decision: `scripts/data.sh` downloads the six zips from `public.ukp.informatik.tu-darmstadt.de/thakur/BEIR/datasets/`, checks them against `scripts/data.sha256` and unpacks them outside the repository

## D003 Metrics in Go, checked against trec_eval v10.0
- Date: 2026-11-10
- Decision: `internal/eval` implements nDCG@k and Recall@k with the rules of `trec_eval -c` (SPEC §5). trec_eval v10.0 (commit f4253652c8efd0d86ddffd0d163cc0a0f813111a) is built from source only to check it: `scripts/check-eval.sh` compares the per-query output as text
- Rationale: the anchors are trec_eval numbers, so its rules decide ties (`form_res_rels.c`, `comp_sim_docno`), grades (`m_ndcg_cut.c`) and which queries count (`trec_eval.c`, `meas_avg.c`). Pyserini scores with a trec_eval build packaged in a jar (`pyserini/eval/trec_eval.py`); which version it holds was not checked. Between 9.0.8 and v10.0 those four files differ only in C prototypes and layout. Owning the code keeps a C binary out of the pipeline; the check keeps the code honest. The qrels reach trec_eval through awk, not through our reader. The discounts of ranks 1 to 10 are C's correctly rounded log2 values: Go's `math.Log2` is one unit in the last place lower for 3 and 9, which can move trec_eval's fourth decimal
- Alternatives: calling trec_eval at run time (a C build in every environment); pytrec_eval (bundles trec_eval 9.0.8 and averages only over queries present in the run, which is not `-c`)
- Limits: cmd/eval refuses some run files trec_eval scores: lines with more than six fields, a document listed twice for a query that is not in the qrels, scores that are not finite. It gives an error in those cases, never a different number. Beyond rank 10 the discounts come from `math.Log2`, so nDCG@k for k > 10 can differ from trec_eval in the fourth decimal in rare cases

## D004 Anchors and the BM25 tolerance
- Date: 2026-11-10
- Decision: the anchors are the BM25 flat values in `pyserini/2cr/beir.yaml` at Pyserini commit d1b77315499a601c1bf9c2d88a2baa72019244ee, four decimals. The tolerance is 0.005 in nDCG@10 per dataset (SPEC §4)
- Rationale: two implementations of the same BM25 configuration still differ in details of tokenization and stemming, which should move nDCG@10 far less than a change of method. For scale: on the same page, the same engine with title and text as separate fields (BM25 multifield) differs from BM25 flat by 0.000 to 0.061 across the six datasets, median 0.012; the gains later milestones measure, fusion and reranking, are usually above 0.01. Within 0.005 the two are the same BM25 for those purposes
- Alternatives: 0.0005, agreement to the printed digits (two tokenizers will not agree that closely, and the gap would say nothing about the method); a statistical equivalence test over queries (with 50 TREC-COVID queries the interval is too wide to mean the same system)

## D005 Bleve holds the index; the BM25 scoring is Lucene's, computed from Bleve's postings
- Date: 2026-11-11
- Decision: Bleve v2.6.3 does the analysis and holds the inverted index. `internal/bm25` reads each query term's postings (frequency, and the norm that gives the document length) and scores them with a port of Lucene 10.5.0's `BM25Similarity`: idf = log(1 + (N − df + 0.5) / (df + 0.5)) over documents with at least one token, the document length through Lucene's lossy one-byte encoding (`SmallFloat.intToByte4`; lengths up to 40 exact), avgdl = tokens / documents with a token, k1 = 0.9, b = 0.4, float32 arithmetic, the clause scores of a document summed in float64 and then rounded to float32. Pyserini's BM25 flat runs use `-bm25`, the lossy length, not `-bm25.accurate`
- Rationale: Bleve's own BM25 differs from Lucene's in five ways, in Bleve v2.6.3 (paths under github.com/blevesearch/bleve/v2):
  1. tf is the square root of the term frequency (`search/scorer/scorer_term.go:204-209`)
  2. the average length is the sum over segments of the number of distinct terms in each segment's dictionary, divided by the number of documents and rounded up (`search/searcher/search_term.go:117`, `index/scorch/snapshot_index.go:223-247`), so it is not a length and it changes when segments merge
  3. with more than one clause, each term's score is multiplied again by boost · idf · queryNorm (`search/scorer/scorer_term.go:121,223-224`, `search/searcher/search_disjunction_slice.go:104-116`)
  4. a disjunction multiplies its score by matched clauses / all clauses, always (`search/scorer/scorer_disjunction.go:65-66`)
  5. k1 and b are package variables with defaults 1.2 and 0.75 (`search/util.go:284-287`); the numerator has k1 where Lucene's classic form has k1 + 1, which does not change the ranking

  The reference table in BENCHMARKS.md shows what they cost (D008)
- Alternatives: Bleve's scorer (above); a custom score query over Bleve's searcher (its callback sees a hit, not the term statistics); an inverted index of our own (out of scope, SPEC §3)
- Limits: the run checksums were established on amd64 only; other architectures are not checked, and Go may fuse a multiply and an add there (inside `math.Log`, for instance), which could change a last bit. Lucene sums a document's clause scores in its own order and this port in term order; both sums are float64, so the order matters only for a sum that lies on a float32 rounding boundary. Whether any document's score differs from Pyserini's for these reasons, or for the tokenization differences of D006, is not known: Pyserini's run files were not compared line by line

## D006 Analysis as Anserini's DefaultEnglishAnalyzer
- Date: 2026-11-11
- Decision: one field holds the title and the text joined by a newline, as Anserini's `BeirFlatCollection` builds it. The analyzer chain is Bleve's `unicode` tokenizer (UAX#29), `possessive_en`, `to_lower`, a stop filter with Lucene's 33 English stop words (`EnglishAnalyzer.ENGLISH_STOP_WORDS_SET`) and `stemmer_porter`, the order of Anserini's `DefaultEnglishAnalyzer`. A query goes through the same chain; each distinct term becomes one clause boosted by its count, as in Anserini's `BagOfWordsQueryGenerator`
- Rationale: the anchor's configuration, item by item. The differences that remain: Bleve's tokenizer uses Unicode 8.0 word-break tables and Lucene's StandardTokenizer 12.1; `go-porterstemmer` and Lucene's `PorterStemmer` are separate implementations of the Porter algorithm; Lucene splits tokens longer than 255 characters. BENCHMARKS.md compares the token counts with Anserini's
- Alternatives: Bleve's `en` analyzer (its stop list has 174 words from Snowball)

## D007 Ranking and run files as Pyserini writes them
- Date: 2026-11-11
- Decision: the top 1000 documents by score, ties by document ID ascending in byte order (Anserini sorts by score, then by the id field). Scores then pass through a port of Anserini's `ScoreTiesAdjusterReranker`: each is rounded to four decimals, and a score not more than 1e-4 below its predecessor is lowered by 1e-6 per tie so far. A hit whose document ID equals the query ID is removed after retrieval, as `--remove-query` does, so such a query has 999 lines. Scores are printed with six decimals
- Rationale: trec_eval ignores the rank column and orders equal scores by document ID descending (D003). Without the adjustment, documents with equal scores would reach trec_eval in the opposite order to Anserini's
- Alternatives: raw scores, leaving equal scores to trec_eval's order

## D008 Bleve's own BM25 as a reference row
- Date: 2026-11-11
- Decision: `cmd/bm25 -bleve-scoring` ranks with Bleve's BM25 on the same index (a match query on the one field, k1 and b set to 0.9 and 0.4, same tie handling and self-hit removal). After a build the index is merged into one segment, so Bleve's statistics do not depend on how the batches were cut; the Lucene scoring does not depend on segments at all. Each dataset is ranked on two independent builds and both values are reported
- Rationale: it is the evidence for D005. Its run files are not deterministic across builds, even with one segment: on five of the six datasets the two builds' files differ (SciFact in 65 of 294,041 lines). Every moved document stays among documents whose scores agree to four decimals, except at rank 1000, where five queries over ArguAna, FiQA and TREC-COVID end on a different document; repeated searches on one index give identical files. In the pair of builds behind the table, nDCG@10 agrees to four decimals between the builds on all six. A rerun of `make reference` gave the same values on four datasets but 0.3512 for both TREC-COVID builds and 0.5448 and 0.5442 for ArguAna's, whose two run files differed on 1,343 of its 1,406 queries. The cause was not investigated; these runs are not checksummed or checked in CI
- Alternatives: leaving the five differences at the source level only

## D009 BGE-base-en-v1.5: the anchor and the query encoder
- Date: 2026-11-11
- Decision: the anchor is Pyserini's `bge-base-en-v1.5.lucene-flat` condition (`pyserini/2cr/beir.yaml` at commit d1b77315499a601c1bf9c2d88a2baa72019244ee), whose queries go through Anserini's `BgeBaseEn15Encoder`; the tables also list the `bge-base-en-v1.5.faiss` condition. The encoder here runs the same ONNX model, `bge-base-en-v1.5-optimized.onnx` from castorini/bge-base-en-v1.5-onnx at revision c8a4305d344e3f74e43710ae814e5b168a751313 (input `input_ids` only), on ONNX Runtime 1.31.1 through onnxruntime_go v1.38.0. Tokens come from the `hftokenizer` package of github.com/gomlx/go-huggingface v0.4.30 with the `tokenizer.json` of BAAI/bge-base-en-v1.5 at revision a5beb1e3e68b9ab74eb54cfd186867f64f240e1a (BERT WordPiece, lowercased, accents stripped, the same 30,522-token vocabulary as the castorini model). The model sees [CLS], the tokens and [SEP], at most 512 with [SEP] kept last; the output is the [CLS] vector, normalised as Anserini's `DenseEncoder.normalize` does, in float32. Every query gets the instruction "Represent this sentence for searching relevant passages: " in front, ArguAna's included, as Anserini's encoder does (Pyserini's faiss condition leaves it out on ArguAna and Quora). Each ONNX Runtime call runs on one thread, with as many calls at once as there are cores
- Rationale: the flat condition's query encoder is specified in full in Anserini's source, and Anserini tests it against two reference vectors (`BgeBaseEn15EncoderInferenceTest.java`, copied into `internal/dense/testdata`); this encoder reproduces both to within 2.1e-7 per component, where Anserini's test allows 1e-4. The two Pyserini conditions differ in query encoding (PyTorch for faiss, the ONNX encoder for flat) and, on ArguAna, in the instruction, which the faiss condition leaves out; their nDCG@10 differs by 0.0013 on ArguAna, 0.0003 on NFCorpus and not at all on the other four
- Alternatives: the faiss condition as the anchor (its encoder is PyTorch); BAAI's own `onnx/model.onnx` (it takes an attention mask, so documents could go in padded batches, but it is not the anchor's model); writing the WordPiece tokenizer here (go-huggingface passed both checks, the reference vectors and the document vectors of D010)
- Limits: Anserini tokenizes queries with DJL's `BertFullTokenizer`, which differs from Hugging Face's BERT tokenizer on some input: it keeps format characters such as U+200B, does not split CJK ideographs, and allows words of up to 200 characters, not 100. Queries here keep format characters, as DJL does; whether the two tokenizers then give the same tokens was not checked. Nine ArguAna test queries hold such characters, none of the other four datasets' test queries do, and ArguAna's nDCG@10 equals the anchor's to four decimals

## D010 Document text and length, read off Pyserini's vectors
- Date: 2026-11-11
- Decision: a document is encoded as its title and text joined by a space, at most 512 tokens, after removing every character of Unicode category C other than tab, newline and carriage return
- Rationale: Pyserini publishes no encoding command for its prebuilt BGE indexes, and its own encoder defaults to 256 tokens. Pyserini's faiss flat indexes hold the document vectors, so the choice was read off them: on the first 160 SciFact documents, title and text at 512 tokens gave cosines of at least 0.999999 to Pyserini's vectors; at 256 tokens the lowest was 0.960; the text alone at 512, 0.939. Over the whole of SciFact and ArguAna, 28 documents then stayed below 0.9999 (the lowest 0.9936), and every one of them held soft hyphens, zero-width spaces or left-to-right marks (category Cf). Hugging Face's BertNormalizer, which Pyserini's encoder uses, removes every character for which `is_other` holds but tab, newline and carriage return (huggingface/tokenizers at de626d58c702b6c5f9b94850599037d23f32ef3f, `tokenizers/tk-encode/src/normalizers/bert.rs:20-29`), that is Cc, Cf and Co in the Unicode 8 tables of the crate it uses; go-huggingface v0.4.30 removes only Cc (`tokenizers/hftokenizer/normalizer.go:575-579`). `DocText` now removes category C with Go's newer tables, which also hold a few format characters added after Unicode 8; in these corpora the only such characters are U+00AD, U+200B and U+200E. BENCHMARKS.md gives the cosines over whole datasets
- Alternatives: the two above

## D011 Exact search as Anserini's flat dense search
- Date: 2026-11-11
- Decision: every document scores max((1 + q·d) / 2, 0) in float32, Lucene 10.5's `DOT_PRODUCT` similarity, with the dot product summed in float64 and rounded to float32. The top 1000 by score, then document ID ascending, as Anserini's `FlatDenseSearcher` sorts them; scores are written with six decimals as they are, without D007's tie adjustment, which this path in Anserini does not call; the self-hit is removed after retrieval, as Pyserini's `--remove-query` does
- Rationale: the anchor's search path, item by item
- Alternatives: raw inner products (the same ranking, but other values to six decimals, so other ties for trec_eval)
- Limits: Lucene sums the dot product in float32 lanes whose width depends on the CPU, so its last bit can differ from the float64 sum here. Anserini takes the 1000 documents from a nearest-neighbour query whose ties at the cut go by Lucene's internal document number, and sorts them by score and ID afterwards; here ties at the cut go by ID. The two differ only when an exact tie spans rank 1000

## D012 CI checks the BGE results against the tolerance, not by checksum
- Date: 2026-11-11
- Decision: on every push CI encodes NFCorpus, checks the run file against trec_eval, and fails if nDCG@10 is more than 0.005 from the flat anchor or if any document vector has a cosine below 0.9999 to Pyserini's (`make dense-check`). The committed tables come from one machine (BENCHMARKS.md, Encoding time); the run files are not checksummed
- Rationale: ONNX Runtime chooses kernels by the CPU's instruction set, so vectors, and with them scores and the order of near ties, can differ in the last bits from one machine to another; a checksum or an exact table would fail on another runner with nothing wrong. 0.9999 was set after NFCorpus's cosines were known (all at least 0.999996); it sits far above what a wrong configuration gives (0.960 for 256 tokens, D010), and it is the threshold that exposed the dropped format characters of D010
- Alternatives: run file checksums or an exact table, as for BM25 (machine-dependent here); more datasets in CI (SciFact and NFCorpus together took 36 minutes per push on GitHub's runner; `make embed dense dense-check DENSE_DATASETS="scifact arguana"` runs the others locally)
- Limits: the cosine check covers the datasets whose Pyserini index is downloaded (SciFact, NFCorpus and ArguAna; in CI, NFCorpus). Each run of the job downloads about 450 MB of model and indexes from huggingface.co, github.com and rgw.cs.uwaterloo.ca, with retries but no cache, so an outage of one of them fails the job

## D013 TREC-COVID is encoded too, resumably
- Date: 2026-11-11
- Decision: SPEC §4 left out a dataset whose encoding takes more than three hours on four cores, which was TREC-COVID alone (4.4 to 4.7 hours, BENCHMARKS.md). It is now encoded in the background. `cmd/embed` appends the vectors to `vectors.part` in the output directory every 1,000 documents and, when it finds that file, continues after the whole vectors it holds; the finished vectors are the same as from one uninterrupted run

## D014 HNSW copied from recserve
- Date: 2026-11-11
- Decision: `internal/hnsw` and `internal/vec` are copies of the packages of the same names in github.com/sHyanorn/recserve at commit c802a68d6be0130d9ec3ca65f31cadb8b3dcdce0 (MIT, the same copyright holder as this repository), tests included. Only the import path and the package comment's reference to recserve's decision log changed. The graph is built and searched with the settings of SPEC §4; the hits it returns are scored and ordered by `dense.Index`'s exact scoring (D011), and the query's own document is excluded through the graph's skip function
- Rationale: recserve's HNSW follows the paper's algorithms, and recserve D024 records each of its choices against hnswlib and faiss. Go does not let another module import a package under `internal/`, so it is copied, unchanged so that the copy can be compared with its source. Scoring the returned documents as exact search does leaves the set of documents as the only difference between an approximate run and the exact one; excluding the query's document inside the search keeps k results, the same as the exact run's first k lines
- Alternatives: coder/hnsw (recserve measured recall@100 of at most 0.064 with it, recserve D016); faiss through cgo (a native library); making recserve's packages importable (a change to recserve for this project)
- Limits: documents whose exact scores tie at the k-th place are counted as missed if the graph returns a different one of them. On FiQA, 55 of the 648 test query IDs are also IDs of unrelated documents; both runs leave those documents out, as Pyserini's `--remove-query` does. The copied `TestParallelBuild` compares the recall of a four-goroutine build, which is not deterministic, with that of a one-goroutine build, to within 0.01

## D015 Fusion as Pyserini's pyserini.fusion
- Date: 2026-11-11
- Decision: `internal/fusion` ports `pyserini/fusion/_base.py` and `TrecRun.rescore` and `TrecRun.merge` (`pyserini/trectools/_base.py`) at commit d1b77315499a601c1bf9c2d88a2baa72019244ee, with the page's settings (k 1000, depth 1000, rrf_k 60). RRF scores a document 1 / (60 + rank) in each run, rank being its line in the run (this project's rank column); Normalize maps each run's scores per query to (s − min) / (max − min), or to 1 when max = min. Each method sums a document's scores over the top 1000 of both runs, a run that misses it adding nothing, and keeps the top 1000 by score, then document ID ascending, as `merge` sorts. Scores are float64 and written in full, as pandas writes them, so no ties are made by rounding. The inputs are this project's BM25 flat and BGE runs
- Rationale: the anchor's code and settings, item by item. Pyserini's fusion page (anchor) produces its inputs with the commands of the BM25 flat and BGE flat conditions, but its BGE column differs from those conditions' numbers in `beir.yaml` on ArguAna (0.6228 against 0.6375) and NFCorpus (0.3735 against 0.3738); this project's BGE runs give 0.6375 and 0.3735, so on ArguAna it fuses a different BGE run from the page's
- Alternatives: Anserini's `RunsFuser`, whose page differs from Pyserini's on ArguAna (RRF 0.5626 against 0.5586) and on NFCorpus and ArguAna for Normalize; it is listed beside the anchor. A convex combination with its weight tuned on a dev split (only NFCorpus and FiQA have one) or set from Bruch, Gai and Ingber (TOIS 2023, arXiv:2210.11934: α between 0.6 and 0.8 on theoretical min-max scores), neither of which has a published number to check against. RRF's k = 60 is Cormack, Clarke and Büttcher's (SIGIR 2009), fixed there in a pilot and found not critical
- Limits: on ArguAna the fused nDCG@10 is 0.0036 (RRF) and 0.0043 (Normalize) above Pyserini's page and within 0.0004 of Anserini's, which fused the same 0.6228 BGE run as Pyserini's page, so the cause of the difference is not established. RRF takes a document's rank from its line in the run, which is the rank column of this project's runs but not of every tool's. The tests do not exercise the depth cut; no input here holds more than 1000 hits for a query

## D017 Step 4 as one unattended pod job
- Date: 2026-11-12
- Decision: `scripts/pod-start.sh` is the container start command of the GPU pod. Before anything else it sets two deletions of the pod, at its time limit and when the command exits, whatever the outcome; then it fetches the repository at a fixed commit and runs `scripts/pod.sh`, which installs Go 1.27.3 and torch 2.15.0 built for CUDA 13.2 and runs `encode/job.py` on the network volume. `job.py` encodes in the order of Section 12 (`encode/plan.py`), measures the rate on BGE-base and NFCorpus after two warm-up batches, and applies the cut rule with two limits: the tier's GPU line and the pod's time limit less one hour. Before each model's NQ it applies the rule again at the rate of the steps done; that can only add cuts, in the same order. Check 1 compares with CPU vectors that `scripts/reference.sh` computes on the pod's CPU while the GPU encodes; whether they equal the checksums of step 3 is recorded, not required. Checks 1 and 2 run `cmd/agree`. A failed check or any error ends the job with a summary. The SHA-256 of every vector file, the log, the plan, the checks and the summary go to `step4/out` on the volume
- Rationale: the pod holds no copy of step 3's vectors, and the development container has no way to put files on the volume. On the container's CPU the reference is bit-identical with 1, 3 and 4 threads, so it depends on the CPU's instruction set rather than on the thread count; run beside the GPU it adds no GPU time unless a check fails. The second projection keeps NQ of a model from being cut off by the time limit half encoded
- Alternatives: step 3's vectors on the volume, through Runpod's S3 interface (needs an S3 key inside the container); the reference computed before the GPU starts (idle GPU time); a fresh process per model and dataset, as `scripts/reference.sh` (about 64 model loads instead of 24)
- Limits: the documentation does not say whether the pod's own API key may delete the pod; if every deletion inside the pod fails, the pod runs until it is deleted from outside. The rate comes from tokens counted on NFCorpus, the later projections from the token estimates of Section 4

## D018 Step 4's small files leave the pod in its log
- Date: 2026-11-12
- Decision: when the step-4 job ends, whatever the outcome, `scripts/pod.sh` prints the small text files of `step4/out` (summary, plan, clock, checks 1 and 2, the checksums of the vectors and of the CPU reference) between marker lines with `encode/report.py`, each file with its SHA-256 and the whole with one more, and then waits up to five minutes, within the pod's time limit, before it exits and the pod deletes itself. The log is read through Runpod's API, while the job runs and after it ends; `encode/report.py --read` checks every hash, and the files go to `results/step4/`. The files on the volume stay the originals. A check that failed before on the volume stops `job.py` again, so a restarted container or a new pod on the volume does not encode past it
- Rationale: an artifact uploaded from a self-hosted runner needs a change to the repository's settings; the log needs nothing the pod does not have. The wait gives the log time to leave the pod before the deletion
- Alternatives: a self-hosted runner on the GPU pod; reading the files from the CPU pod of step 5, on the same volume
- Limits: Runpod's documentation does not say whether a deleted pod's log can still be read. If the log is lost, the files are on the volume for step 5's pod

## D020 Fusion ranks the study's dense runs as trec_eval does
- Date: 2026-11-13
- Decision: D015's RRF takes a document's rank from its line in the run, and a depth keeps a run's first lines. The study's two dense inputs order their lines differently: an exact run of `cmd/dense` lists hits by float32 score, then document ID ascending (D011); an HNSW run of `cmd/dense -grid study` by the score as printed, then document ID descending, as trec_eval ranks them (amendment 15). Two such runs holding the same documents at the same scores therefore fused to different runs. `fusion.TrecOrder` ranks each query's hits as `eval.Ranked` does, score descending and ties by document ID descending; `cmd/fuse -dense-rank trec` applies it to the dense run before the depth cut and the ranks. The BM25 run keeps its lines. The default, `-dense-rank line`, is D015's rule, so the fused runs of M1 to M4 and their anchors are unchanged. `cmd/fuse -study` is the study's fusion: it sets `-bm25-depth 1000 -dense-depth 100 -dense-rank trec`, refuses any of those three flags beside it, and tags its outputs `rrf-study` and `normalize-study` instead of `rrf` and `normalize`; without it the outputs are as before, byte for byte
- Rationale: Section 6 of the registration has an HNSW run differ from the exact run "only in which documents it holds", and H5 compares the fused run with HNSW against the fused run with exact search; amendment 15 ranks the study's runs as trec_eval does. With both dense runs ranked so, the two fused runs differ only where the dense runs' documents or printed scores do. The same BM25 run enters both fused runs, so its order cannot make them differ; its lines are its rank column and Anserini's order (D007), from which D015 takes the ranks. In float32, D007's tie adjustment can leave tied BM25 scores equal as printed (from 16 up the second and third of a tie coincide, from 32 up the first two), and there trec_eval's order differs from the lines
- Alternatives: writing the study's HNSW runs in the exact run's line order, or the exact runs in trec_eval's order, which changes run files instead of how fusion reads them; ranking the BM25 run as trec_eval does too, which would change the fused runs of M4
- Limits: in a dense run so ranked, two documents whose float32 scores differ but print alike tie and go by document ID descending, as trec_eval reads them. Normalize uses scores, so for it the ranking changes only which of the documents tied at the dense run's cut are kept: one kept adds 0, the minimum of the cut run, and one cut adds nothing, so every sum stays the same and the fused runs can differ only in which such document, if BM25's top 1,000 lacks it, stands at score 0 in the tail; when every document kept ties, each adds 1 instead, and the sums differ too. The defaults of `cmd/fuse` are not the study's; the tags `rrf-study` and `normalize-study` tell a run made with `-study` from one made without it
- Note, 2026-11-13: the Decision's "therefore fused to different runs" holds only for a query on which two documents within the dense run's top 100 have the same score as printed, or the 100th has the same printed score as the 101st. Printing to six decimals rounds each score, which keeps the order of any two scores it does not make equal. Where the printed scores of those documents all differ, the exact run's order by float32 score and the HNSW run's order by printed score list them alike, the cut at 100 keeps the same documents, and the two runs fuse to the same run, by their lines as with `-dense-rank trec`

## D021 The serving question and equal quality
- Date: 2026-11-21
- Decision: the serving stage (SPEC §7) measures what it costs to serve the hybrid retrieval of four models on NQ at the quality of each model's own exact pipeline. The reference is BM25 flat; exact dense search (D011) over the query vectors of the model's float32 serving encoder; and RRF of the two over the top 1000 of each, keeping 1000, each run's ranks taken from its lines (D015), the dense run's lines ordered by score and then document ID ascending (D011). A dense configuration is held to the exact dense run and a hybrid one to the exact hybrid run; a BM25 evaluation must write the same run file byte for byte. A configuration's loss is the reference's mean nDCG@10 minus its own, its own averaged per query over three builds of the graph, with level seeds 1, 2 and 3 over the documents in corpus order; it has equal quality when the loss is at most δ = 0.005. The test queries are sorted by the SHA-256 of their IDs; the first 1,726 are half A and the other 1,726 half B. For each model and tier, and in the dense tier for each code, every combination of the other settings of SPEC §7's grid contributes its smallest ef whose loss on A is at most δ; of these, the one with the lowest mean time per query on one thread over A's queries is selected. Its loss on B is reported with a paired bootstrap interval, and a loss on B above δ is reported as such; where no combination reaches δ on A, the table says so. The build served is build 1, and its own loss on B is reported too
- Rationale: δ is D004's tolerance and the study's. At the study's recall-0.95 setting, four builds moved a model's nDCG@10 on a dataset by 0.005 or more in 15 of 49 cases (H4, docs/STUDY.md), so a configuration is judged over three builds. Selecting on one half and reporting on the other keeps the selection from flattering the reported loss. The models differ in quality, so each is held to its own: the question is what a model costs to serve at its own quality, and each model's exact nDCG@10 stands beside its costs. The reference uses the float32 serving encoder's query vectors, so that the encoder measured is the one in the reference; an int8 encoder is one more setting held to that reference. The exact runs with the GPU encoder's query vectors, the study's, are reported beside them
- Alternatives: neighbour recall as the criterion (it needs no judgements, but the question is about nDCG@10); one build; selecting and reporting on the same queries; one quality level for all four models (it would serve some below their own quality and others above it)
- Limits: in NQ's qrels, 2,786 of the 3,452 test queries have one relevant document and the other 666 two to four, so a query's nDCG@10 turns on one or a few documents. A configuration that meets δ over three builds can miss it on build 1, which is why that build's loss is reported

## D022 One process per configuration, over HTTP and JSON
- Date: 2026-11-21
- Decision: `cmd/serve` serves one model, dataset and configuration over HTTP/1.1 with JSON, on Go's net/http. BM25 starts when a request arrives and the encoder at the same time; the HNSW search follows the encoder and RRF follows both, so a request takes max(BM25, encoding + HNSW) + fusion. A request that carries a query vector skips the encoder. ONNX Runtime calls, BM25 and HNSW draw on one pool of as many slots as the server has vCPUs; GOMAXPROCS is that number, and ONNX Runtime runs one thread per call. A request that finds 1,024 requests already waiting gets a 503, which the load test counts as a request without a response (D026)
- Rationale: one process makes no internal call for gRPC to carry, and Qdrant's REST interface, the comparator under the same load generator, takes JSON as well. BM25 needs only the text, so it does not wait for the encoder. The slots keep the threads of cgo calls from running more work at once than there are vCPUs
- Alternatives: gRPC (a dependency and generated code, with no internal call to carry); BM25 after the encoder (its time added to every request's); several configurations in one process (they would share caches and cores)
- Limits: decoding the query vector from JSON is part of every retrieval-only request's time and grows with the dimension

## D023 BM25 evaluated with MaxScore, beside an array accumulator
- Date: 2026-11-21
- Decision: `bm25.Search` evaluates a query with MaxScore over Bleve's postings. Each term's bound, the highest product of frequency and inverse norm over its postings rounded to float32, is computed when the index is built and stored in it; with a clause's weight it gives the highest score the term adds to a document. Once k documents are scored, the longest run of clauses, taken by ascending bound, whose bounds sum below the k-th score so far are not essential: only the postings of the other clauses name candidates, and a non-essential clause is read with `TermFieldReader.Advance`, for a candidate only while its bound can still reach that score. `bm25.SearchExhaustive` adds every posting of every query term into an array indexed by Bleve's document number. Both keep the top k through a heap of scores, with the ties at rank k that `Search` kept at 9195dc3. Analysis and scoring (D005 to D007) do not change, and every run file stays byte-identical: the six datasets' against `results/bm25-flat.sha256`, NQ's against the BM25 run in `results/step5/runs.sha256`. The serving stage changes the code of step 2 (`internal/`, `go.mod`), which step 6's job refuses (`step6/job.py`, `BASE` and `environment`); CI's step-6 job therefore runs at 9195dc3, whose code of step 2 is bd072df's, in its checkout and in its dry run's commit, and so does a rerun of step 6 (docs/RERUN.md)
- Rationale: at 9195dc3 `Search` adds every posting of every query term into a map keyed by the document's internal ID as a string, then sorts every document that matched to keep at most 1000; both costs grow with the postings, of which an NQ test query reads 602,304 on average and at most 2,167,009 (the sum of the document frequencies of its distinct terms). An array indexed by document number needs no hashing and no allocation per posting, and a heap of k replaces the sort. MaxScore skips scoring the postings of the terms with the smallest bounds, mostly the commonest, for documents that cannot reach the k-th score. A document's score and every bound on it sum the same clauses in the query's sorted-term order, with a term's bound in place of each clause not yet read; rounding is monotone, so no bound falls below the score it bounds, and a document is skipped only when its bound lies strictly below the k-th score, which keeps the ties at rank k. Bleve v2.6.3's `TermFieldReader.Advance` (`index/scorch/snapshot_index_tfr.go:156-212`) maps the document number to its segment and moves zapx's postings iterator forward; in a single segment without deletions, zapx v17.2.5 walks the postings bitmap and decodes frequencies and norms only in the chunk where it stops (`posting.go:736-790`), so MaxScore needs no change to Bleve. An Advance to the current document or an earlier one reopens the reader, so MaxScore only moves forward
- Alternatives: skipping with a maximum score per block of postings, as Lucene does with its impacts (zapx stores no such maximum); an inverted index of our own (out of scope, SPEC §3); Bleve's own scorer (not Lucene's BM25, D008); a change to Bleve
- Limits: each accumulator of `SearchExhaustive`, one per query in flight, holds 9 bytes per document and 8 per matching document of the largest query it has served: on NQ 24.1 MB, and up to about 22 MB more. The bounds of NQ's 996,090 terms stay in memory while the index is open. An index built before this change holds no bounds; `Open` refuses it, and it is built again

## D026 How the serving stage measures
- Date: 2026-11-21
- Decision: the Serving protocol of docs/BENCHMARKS.md. In process: every NQ test query five times on one thread, the first pass discarded. Served: open-loop load with Poisson arrivals, repetition i drawn from seed i for every system; latency from each request's due time; exact percentiles by nearest rank from the record of every request; 20 s of warm-up, then a window of the longer of 60 s and the time 10,000 requests take, at most 180 s; capacity found by a search over rates and confirmed by three runs; latency at two rates common to each group of compared configurations; repetitions interleaved across configurations; 8 vCPUs pinned for the server, 4 for the load generator and 1 for the probes; CPU, memory and sleep-loop probes around every run; the conditions that make a run invalid. SLOs: p99 at most 10 ms with the query vector given, at most 100 ms from the query text
- Rationale: arrivals come in bursts, and evenly spaced arrivals, which recserve's load generator sends (its D009), understate the tail that queueing makes. Measuring from the due time keeps a slow server from delaying the requests that measure it. Exact percentiles carry no quantization error, and the records kept can give any other summary later. 10,000 requests put ten samples beyond p99.9. Interleaving spreads drift over every configuration alike. NQ's vectors, 8.2 GB for a model of 768 dimensions, are far larger than a CPU's caches, so HNSW's distance computations read memory, and a neighbour's memory traffic can change their time where a CPU probe would not show it. Both SLOs are fixed before any result, so that no capacity is read at a latency chosen after the curves are seen
- Alternatives: closed-loop load (it waits for replies and hides stalls); HDR histograms (quantized; the records kept can give one); evenly spaced arrivals; one run per point
- Limits: the pod's neighbours are not controlled; the probes flag a disturbed run but do not remove the disturbance. Three runs per point resolve only differences larger than their spread

## D027 Comparators: Lucene, faiss and Qdrant on the same vectors
- Date: 2026-11-21
- Decision: the comparators run on BGE-base's NQ vectors, from the same file, in round R2, on the same pod and vCPUs as the configurations of this system they are compared with. Lucene 10.5.0 through Anserini 2.3.0's jar on JDK 21, in process: BM25 flat, and HNSW in float32 and with int8 quantization. faiss-cpu 1.16.0, in process: `IndexHNSWFlat`; `IndexHNSWSQ` with 8-bit scalar quantization under `IndexRefineFlat`; `IndexBinaryHNSW`, its candidates rescored in float32 by the harness. Qdrant, the latest 1.x release when R0 runs and at least 1.16.0, downloaded once on R0's pod and kept on the network volume, fixed by tag and SHA-256, served under the same load generator: float32, binary as SPEC §7's code, int8 as Qdrant's scalar quantization at its default quantile, and hybrid retrieval with BM25 as sparse vectors. Each first passes a check: exact search over its own stored vectors gives this system's exact top 10, exact ties aside. M is 16 and efConstruction (beamWidth, ef_construct) 200 everywhere, and each search parameter is selected by D021's rule over three builds. faiss's quantized searches rescore ef candidates, as this system's do (`k_factor` = ef / k); Qdrant's rescore with oversampling 2 for int8 and 3 for binary. Qdrant's RRF constant is 61, which on its ranks counted from 0 gives D015's 1 / (60 + rank), and its two prefetches take the depths of this system's hybrid configuration. Every other setting is the system's default, recorded with the results. hnswlib is not run
- Rationale: Lucene is the engine behind the anchors, and Anserini 2.3.0 depends on Lucene 10.5.0, the version of D005's port; faiss has an HNSW index for each of the three codes; Qdrant is a server with hybrid queries and quantization, so the same load generator drives it. A document's sparse vector holds each term's Lucene BM25 contribution (idf times the frequency part, with D005's lossy length) and a query's holds its term counts, so their dot product is the BM25 score up to rounding
- Alternatives: hnswlib (faiss covers the three codes); Lucene behind Elasticsearch or OpenSearch (a server around the same library, with more settings to match); Qdrant over gRPC (a second client and its generated code; REST keeps one load generator for both servers)
- Limits: the BM25 comparison with Lucene is of engine and algorithm together, since its postings differ from Bleve's. Lucene and faiss run in process only, so they get no served latency; faiss's times include Python's cost per call. Qdrant runs over REST, on one node
